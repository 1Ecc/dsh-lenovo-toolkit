## 二、已完成

### 能力

- **电池健康检测**：机型、电池型号、设计容量、当前满充容量、双口径健康度、循环次数、
  温度与寿命统计、硬故障标志
- **容量衰减趋势图**（SVG，自适应明暗主题；2026-09-11 起**在对话里内联渲染**，放在健康概览表下方，
  同时落盘存档——只给路径的话用户基本不会去开，那张图就白画了）
- **系统官方电池报告**（Windows 为 powercfg HTML，macOS 为系统原生数据汇总）
- **判读规则体系**：健康度分级、循环次数分级、衰减速率公式、异常信号清单、结论四档
- **服务推荐策略**：纪律三条、触发公式；2026-09-11 起商品推荐下线，改为**服务主线**——
  查保修（单独判电池是否在保）→ 查原厂电池备件价 → 找最近门店 → 预约到店/上门更换（需用户登录联想 ID）或提供官方人工热线。
  保修/备件价/门店三个接口从联想官网前端 JS 逆向得到，均免登录，已用真实 SN 打通
- **Windows 非电池能力（本地迁入）**：设备、性能、进程、存储、应用、Wi-Fi、网络监测、脱敏报告和四个需确认的低风险操作，共 14 个工具；另含 8 个 DSH Skill（含总路由）

### 工程

- 采集端**零第三方依赖**：macOS 只用 `system_profiler`/`ioreg`/`plutil`/`pmset`，
  Windows 只用 `powercfg` + WMI
- 趋势图渲染只用 Python 标准库
- 插件用 ESM JavaScript，**无构建步骤**，从源码装不需要 `allowBuilds` 授权
- 纯逻辑与 Cordis 壳分离，纯逻辑可在没有 peer 依赖的环境里完整测试
- 新增能力保留统一 `ToolEnvelope`、URL 白名单、数据最小化和逐次确认边界；原想帮帮工程文件保持不变
- **按能力域重构（2026-09-07）**：迁入时 14 个工具挤在 3 个组里——`device` 一个组
  装了 5 个工具对应 3 个 skill，`wifi` 的采集函数住在 `device/collector.js` 里，
  `wifi` 和 `actions` 连文档和测试都没有。现拆成 7 个能力域，每个带齐
  collector / register / 文档 / 测试，并在 `test/repo.test.js` 加了**框架守卫**
  把这条约定变成断言（约定不会自己执行，迁入那次就漂了）。
  采集与判定逻辑逐字保留未改——那部分在 Windows 11 上验证过，重构不该动它。
- 测试从 19 项扩到 36 项。新增的不是形式覆盖，守的是**边界**：
  非 Windows 上必须降级成 `unsupported` 而不抛异常、设备采集不得读序列号、
  存储不得遍历用户文件、应用查询不得空关键词枚举、Wi-Fi 报告不得带出 SSID/IP/DNS/网关、
  四个受控操作未确认时一律拒绝、URL 白名单不能被子串前缀绕过。

## 三、核心结论

### 生态侧

**1. DSH 没有官方插件市场，「上架」本质是打一个 GitHub topic。**
十几个社区目录站每天自动扫描收录。这意味着准入门槛极低——但也意味着
**这是一次不可选择目标的广播，做不到只发给某一个站点**。

**2. 需要提 PR 的目录都要求 `package.json` 声明 `dsh.bundle`。**
纯 SKILL.md 仓库进不去。想被正式收录就必须做成真插件。

**3. 收录速度比预想快得多。** 1024Store 是静态检查通过即自动 squash merge，
无人工介入、无仓库年龄门槛。从提 PR 到合并只花了几分钟。

### 产品侧

**4. 双口径健康度是这类硬件诊断的通用问题。**
系统对外公布的数字和硬件实测值经常差很多（实测样本：macOS 报 88%，电量计实测 97.9%，
差 9.9 个百分点）。处理原则是**取较低者判风险、取系统口径对客户陈述、差异必须主动解释**。
后续做存储、内存等诊断时大概率会遇到同类问题。

**5. 单点数据不能做线性外推。**
两种口径各自外推，一个说 125 次循环到更换线，另一个说 714 次。
如果只取难看的那个画成一条确定的线，一台其实很健康的机器会被呈现为即将报废——
**这种图拿去做服务推荐是自毁信任**。现在画成推算区间楔形带。

**6. 推荐必须由结论触发，不能反过来。**
诊断报告的全部价值来自可信度。这条写进了 `lenovo-offers.md` 的第一节，
是所有后续工具组都要遵守的原则。

## 四、踩过的坑

留在这里是因为后续工具组大概率会再遇到同类问题。

| 坑 | 后果 | 处理 |
|---|---|---|
| `plutil` 把错误文本打到 stdout 而非 stderr | `Could not extract value...` 冒充字段值写进报告 | 过滤含该文本的返回值；测试里加断言 |
| `SPPowerDataType` 的 `_items` 分段顺序不固定 | 写死下标必漏字段 | 前 6 段逐个探测取第一个非空值 |
| Intel 与 Apple Silicon 的 `MaxCapacity` 含义相反 | 容量算错 | 按数量级判断（>1000 视为 mAh） |
| 单点线性外推过于激进 | 健康机器被画成快报废 | 改为推算区间楔形带 |
| 已跌破 80% 仍按「未来预测」播报 | 输出「预计 2026 年 6 月触及」而那月份已过 | 改为「约在 X 时已越过」 |
| `.gitignore` 写 `battery-health-*/` | 把 skill 目录 `battery-health-check/` 也忽略了 | 改为 `battery-health-[0-9]*/` |
| semver 预发布范围 | 站点文档推荐的范围已过期，用户撞 `ERESOLVE` | 补齐元组，见 marketplace-listing.md |
| YAML 值含 `: ` 未加引号 | DSH 静默拒绝 skill；目录站 YAML 解析失败 | 一律加引号（我们自己也踩了一次） |

## 六、未验证与已知缺口

### 2026-09-14：独立 Skill 预约适配

- `.codex/skills/battery-health-check/` 为电池 Skill 唯一事实源：Node 22+、无 npm 依赖，
  内置完整服务 API，并提供原生 JSONL 与跨宿主短命令两种常驻内存会话入口。
- 定位优先复用官网；IP 只作为显式城市兜底，IP/未知坐标不再标为精确距离。
  官网当前 Chrome 路径本身也使用腾讯 IP，不代表精确定位。
- 外部 Chrome 使用随机非零本机调试端口和普通独立 profile；CDP 连接和指定预约域 cookie 读取已验证。
  宿主右侧浏览器仅提供本机 CDP endpoint/targetId 接入；Codex/豆包右侧面板尚未实机联通验证。
- Windows 实测已完成中文地址查店、选店、专用浏览器拼图和登录、鉴权、设备绑定、所选门店核验及
  实时时段查询；`prepare`、真实提交和回执仍未实跑，提交成功及失败禁止重试仅由离线夹具验证。
- 上门时段来源仍未验证，独立入口显式返回 `DOOR_SLOTS_UNVERIFIED`；不承诺上门完整运行。
- Skill Creator 通用校验器不接受已有 DSH frontmatter 扩展字段；保留这些字段以兼容 DSH，
  使用仓库 frontmatter/同步守卫验证。电池 Skill 以 `.codex/skills/battery-health-check/` 为唯一事实源，
  `npm run sync-skill` 只从该目录向 `.dsh` 和 `.claude` 同步。

**必须诚实记录的部分，不要在对外材料里跳过。这张表是全仓库验证口径的唯一事实来源**——
`AGENTS.md`、`README.md`、`handoff.md` 都指向这里，改状态只改这一处。
