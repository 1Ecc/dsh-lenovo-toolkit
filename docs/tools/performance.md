# 能力域：性能与进程

回答「怎么这么卡」。

| 项 | 值 |
|---|---|
| 工具 | `performance_get_status` · `process_list` |
| skill | `.dsh/skills/performance-diagnosis/` |
| 平台 | 仅 Windows |
| 数据源 | Windows CIM + 性能计数器（`Win32_PerfFormattedData_PerfProc_Process`） |

## 工具

| 工具 | 返回 |
|---|---|
| `performance_get_status` | CPU 占用 %、内存占用 %、可用内存 GB、开机时长秒、逻辑处理器数 |
| `process_list` | 按 `cpu`（默认）或 `memory` 排序的高占用进程，1～20 条，默认 5 |

## 两条口径纪律

**① 这是时点快照。** 两个工具都在 `warnings` 里带这句话，判读时必须转述。
卡顿投诉里最常见的误判就是拿一次采样当「长期高占用」的证据——
用户抱怨的往往是「有时候卡」，而一次快照对「有时候」没有任何证明力。
证据不足时按 `AGENTS.md` 第 2 条给区间和条件，不要给假装精确的结论。

**② 进程 CPU 是按逻辑核总量归一化后的近似值**（`PercentProcessorTime / 逻辑核数`），
和任务管理器的数字未必逐位对齐。`cpu_metric` 字段里写明了这一点，
不要在报告里把它讲成「任务管理器显示的占用率」。

短时进程可能在采集期间启动或退出，所以进程列表不是完备快照。

## 边界

不返回命令行参数和完整可执行路径——那会把用户在跑什么、装在哪暴露出来，
而「哪个进程吃 CPU」这个结论只需要进程名。
