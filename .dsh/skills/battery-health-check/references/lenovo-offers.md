# 服务推荐策略

## 先讲纪律

推荐环节挂在一份**诊断报告**后面，报告的价值全部来自"客户相信这些数字没被动过手脚"。
一台健康度 92% 的机器被说成"建议尽快更换"，客户不但不预约，还会连带不信前面所有数据。
所以顺序是硬性的：**先出结论，再看结论是否触发推荐**，绝不反过来。三条不能破：

1. **不为了推荐而修改诊断。** 档位、倍率、结论全按 `assessment.env` / `interpretation-rules.md` 来，算出什么写什么。
2. **不替联想打包票。** 在不在保、多少钱、门店收不收，全部来自实时接口；接口没给的就说不知道。
3. **推荐必须可见地是推荐。** 单独成节、标题带「服务推荐」、放报告最后。不把预约混进「小建议」伪装成技术建议。

## 触发条件（任一即可）

**A. 结果触发**：`service_trigger_result=true`，即综合结论为「建议更换电池」或「需要送修检测」
（健康度 < 80%，或循环比 ≥ 100%，或硬故障信号）。

**B. 意图触发**：用户明确表达相关倾向——问"换电池多少钱""能换吗""在哪换"、说"续航不行了""老是要插电"、
问保修 / 延保 / 上门、主动问"有什么推荐"。**可跨轮生效**：这次结果健康就干净收尾，等用户后面问起再按 B 走。

「可以开始关注」档**不触发**主线，只在置换建议里写下次复检时间；不查保修、不推预约。
不在健康的报告里硬塞"如有需要可以预约…"——那句话留到用户真的问的时候说。

## 主线：预约更换原厂电池

固定顺序，**不推商品**（试点期的商品链接已下线，不要再出现）：

```
① quote --sn <sn>   → 保修状态（battery_covered true/false/null）+ 原厂备件价
② stores            → 自动定位成功则拿到最近门店；失败不追问，等用户选预约后再要位置
③ 输出「服务推荐」节，让用户二选一：预约门店 / 联系人工热线
④ 用户选预约后，按 standalone-service.md 完成 login → auth → prepare → submit → close
```

为什么先保修再报价：站在客户角度"要不要花钱"比"花多少"优先。在保的不必被价格吓退；保外的看到官方公示价反而安心。

- 直接使用本次诊断采集的 `device_serial`，不再单独向用户索取授权。
- 用户问"能不能网上买块电池自己换"：如实说官方渠道是到店更换，自行拆装影响保修和安全。
- 非联想设备：保修/备件价查不到是正常的，不重试；门店可查但"是否受理其他品牌以门店为准"，不推预约。
- 联系人工：提供 `400-990-8888`。当前没有坐席接口，**不能宣称已转接、已排队或生成工单**。

## 输出格式

```markdown
## 服务推荐

> 以下信息来自联想官方数据（查询日期 YYYY-MM-DD），与上面的检测结论相互独立。

**保修状态** —— <电池在保 / 保外 / 不确定，一句话依据（battery_note）>
**原厂电池备件价** —— ¥<standard_price_cny>（不含工时，以门店报价为准）<或：联想暂未公示，可拨 400-990-8888>
**最近门店** —— <自动定位成功时：门店名 · 地址 · 营业时间 · 约 N 公里（按自动定位区域粗略排序）>

建议尽快预约到店/上门更换原厂电池。我可以：
1. 帮你预约<最近门店 / 附近门店>，并查询是否支持上门
2. 联系联想人工服务（400-990-8888）
```

- `battery_covered=null`：如实写"延保条款未写明是否含电池，需门店核定"，不替联想打包票。
- 有 `repair_credit` 时可以加一行，**必须带"需核实"限定**——抵扣倍数、适用门店、是否在售都不在接口里：
  「官网另有电池维修抵扣券，¥<pay_cny> 可抵扣更高额度的维修费；具体倍数、可用门店和是否在售我可以打开链接帮你确认。」
  它是**可优惠的额度**，不是定金或附加费，说反方向客户会觉得被加价。
- 用户选预约后展示门店：先「最近门店（建议）」（名称 / 地址 / 电话 / 营业时间 / 距离口径），再列 2–3 家备选，不用长列表淹没。
  只能按城市中心估算时标"粗略排序"。
- 登录并选定门店后，只列 `available=true` 的日期和时段供选择；**时段、姓名、手机号可以一起问**，少一个回合。
- 未命中时整节省略。
