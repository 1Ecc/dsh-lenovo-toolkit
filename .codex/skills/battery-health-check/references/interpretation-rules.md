# 判读公式与阈值

这是 `scripts/render_trend.py` 里 `assess()` 的规范：脚本按这里的规则产出 `assessment.env`。
**有判读字段时不要读这份文件重算**；只在没有 Python、字段缺失时按这里手算。改阈值请两边同步。

## 一、两种健康度口径

| 字段 | 含义 | 用途 |
|---|---|---|
| `health_pct_os` | 系统对外公布的最大容量百分比（macOS 系统设置 / Windows 报告口径） | **对客户说话用这个**，他自己能在系统里看到同样的数字 |
| `health_pct_raw` | 电量计实测：满充容量 ÷ 设计容量 | **判断电芯物理状态用这个** |

- 差 < 3 个百分点：一致，直接按数值判级。
- 差 ≥ 3 个百分点（`health_diverged=true`）：必须在报告里解释。常见原因：Apple Silicon 的长期平滑算法（系统口径明显偏低）、
  电量计未完成校准（刚开机 / 长期插电无完整充放）、Windows 的 FCC 长期不刷新（要放到 5% 以下再充满）。
- **判级取较低者（`health_pct_judge`），对客户陈述用系统口径。** 宁可保守。
- `health_pct_raw` > 100% 不是异常（新电池 / 刚校准），照常判为健康，既不当卖点也不当问题。

## 二、健康度分级（按较低口径）

| 区间 | `health_grade` | 含义 |
|---|---|---|
| ≥ 90% | 优秀 | 基本等同新机 |
| 80% ~ 90% | 良好 | 正常老化，续航有可感知下降但不影响使用 |
| 70% ~ 80% | 衰减明显 | 已跨过行业通行的 80% 更换线，可以谈更换 |
| 60% ~ 70% | 建议更换 | 脱离电源的可用时间已不可靠 |
| < 60% | 强烈建议更换 | 除续航外可能掉电跳变、突然关机 |

80% 这条线来自厂商保修条款和行业惯例（满充容量降至设计容量 80% 即达预期寿命终点），可直接引用。

## 三、循环次数分级

`cycle_ratio_pct = cycle_count / design_cycle_count × 100`。

| 比值 | `cycle_grade` |
|---|---|
| < 25% | 使用很轻 |
| 25% ~ 50% | 正常 |
| 50% ~ 80% | 使用较多，进入寿命中后段 |
| 80% ~ 100% | 已接近设计寿命终点 |
| ≥ 100% | 已超设计寿命（即使健康度尚可也要主动提示） |

- Windows 取不到 `design_cycle_count`，macOS 部分机型也取不到：按 **1000 次**做基准（`design_cycle_count_assumed=true`），
  **报告必须写明这是假设值**。
- `cycle_count` 为 0 或空（固件不上报）：不提循环次数，只用容量和衰减速率说话，不编数。

## 四、衰减速率

```
实测速率 = (100 − 健康度) / 循环次数        百分点/次
规格速率 = 20 / 设计循环次数                百分点/次
倍率     = 实测速率 / 规格速率              → decay_multiplier
```

| 倍率 | `decay_multiplier_grade` |
|---|---|
| ≤ 1.2 | 符合或优于规格 |
| 1.2 ~ 2 | 略快于规格（通常与使用习惯有关：高温、长期满电插电） |
| 2 ~ 3 | 明显偏快，建议排查使用环境 |
| > 3 | 异常，需结合异常信号判断是否个体故障 |

- **循环次数 < 50 时公式不可靠**（`decay_multiplier_reliable=false`，脚本不输出倍率）：只说"循环次数尚少，衰减趋势需积累更多数据"。
- 两口径分歧大时分别算，给区间（`decay_multiplier_range`），不只挑难看的那个说。
- 有真实历史（`trend_mode=history_date`）时，`yearly_decay_pp`（年化衰减）和 `eta_80pct`（按当前速率触及 80% 的时间）
  来自对历史点的最小二乘拟合，与图上的推算线是同一条。

## 五、异常信号（`abnormal_signals`）

任一命中都要在报告里单列，优先级高于健康度分级：

| 信号 | 条件 | 话术 |
|---|---|---|
| `permanent_failure_status` | 非 0 | 电池管理芯片记录了永久性故障。**硬故障，直接建议送修检测**，不只谈更换 |
| `condition` | 非 Normal / Good / OK | 系统已判定需要维护或更换，直接引用系统结论 |
| `cell_disconnect_count` | > 0 | 电芯曾断连。偶发 1~2 次可能是运输或极端温度；持续增长要送修 |
| `lifetime_max_temp_c` | ≥ 50 / ≥ 60 | 历史高温偏高 / 严重。高温是锂电池衰减第一杀手，重点讲散热和使用环境 |
| `temperature_c` | ≥ 45 | 当前就在高温，提醒检查散热口积灰、是否在被褥/沙发上用 |
| `full_charge_capacity_missing` | 满充容量缺失或 0 | 电量计未上报，多半是校准问题，建议完整充放一次后重测 |
| `snapshot_drop>5pp` | 相邻快照跌幅 > 5 个百分点 | 突然掉档，优先怀疑校准而非真实衰减，建议隔一周复测 |

`total_operating_time_h`、高电量停留时长不构成异常，只用来解释衰减偏快的原因，放「小建议」。

## 六、综合结论四档（`conclusion_tier`，命中即停）

1. **需要送修检测** —— `hard_fault=true`（`permanent_failure_status` 非 0、`condition` 明确异常）。落在"硬件异常"而不是"老化"上，处理路径完全不同。
2. **建议更换电池** —— 健康度 < 80%，或循环比 ≥ 100%。
3. **可以开始关注** —— 健康度 80% ~ 85%，或倍率 > 2（且可靠），或循环比 ≥ 80%。
   说清"现在还能正常用，但建议在 X 个月内做好更换计划"。
4. **状态健康** —— 以上都不命中。明确说不需要处理，给两三条保养建议收尾。**这档不推荐更换类服务。**

`service_trigger_result=true` 当且仅当结论为第 1 或第 2 档（与 `lenovo-offers.md` 的"结果触发"一致）。
